# Minecraft: ONE

---

Minecraft: ONE은 현재 양분된 Minecraft의 생태계를 통합하는 목표를 지닌 가상의 신규 Minecraft 에디션이다.

ONE이라는 이름에는 총 두 가지의 각기 다른 뜻이 담겨있다. 첫 번째 뜻은 Minecraft의 공식적인 차원들인 Overworld, Nether, End를 나열한 역두문자어이다. 두 번째 뜻은 Microsoft가 자사 브랜드 명명에 주로 사용하는 단어 중 하나인 One의 연장선상이며, 이는 _하&#xB098;_&#xB85C; 통합한다는 Minecraft: ONE의 목표에 대응한다.

## 시스템

---

### 개발

---

Minecraft: ONE은 Unity로 대표되는 상용 엔진 대신 자체적으로 개발된 게임 엔진인 RenderDragon을 사용한다. 상용 엔진은 주로 폴리곤 기반의 메시를 사용하기에 복셀 기반 게임인 Minecraft에는 적합하지 않았다. RenderDragon은 Bedrock Edition에 적용되며 실사용 환경에서의 선례가 존재하는 엔진이다.

게임의 근본적인 실행 속도를 결정하는 그래픽 렌더링과 물리 엔진에는 Bedrock Edition과 동일하게 C++을 주로 사용한다. C++은 Java, C# 등과 달리 런타임이 없기에 게임 도중 일시적인 프리징을 유발하는 가비지 컬렉터가 포함되어 있지 않다. 이에 더해 개발자가 메모리를 직접 조작하는 경로를 지원하여 타 언어로는 어려운 수준의 네이티브 최적화를 가능케 한다. 단, 이러한 장점에 따른 댕글링 포인터, 이중 해제, 메모리 누수 등의 비정상 종료나 데이터 손상을 유발하는 메모리 해제 관련 오류들을 방지하기 위해 추후 서술할 함수 포인터의 사용을 제외하고는 반드시 스마트 포인터를 사용하며, 메모리 풀링과 단편화 방지를 위하여 최적화가 필요한 부분에 커스텀 얼로케이터를 도입한다.

반면 대부분의 전체 코드 베이스가 C++로 작성된 Bedrock Edition과 달리, Minecraft: ONE은 인게임 콘텐츠 등의 게임 엔진을 제외한 상위 차원 로직에는 .NET 10 런타임 기반의 C#을 적용한다. 앞서 언급하였듯이 C++에 비하면 최적화 측면에서 부족한 측면이 분명히 존재하나, 이러한 선택지를 채택한 이유에는 크게 세 가지 이유가 존재한다.

첫 번째 이유는 고수준 언어의 필요성이다. 앞서 언급하였듯이, 게임의 핵심 엔진과 물리 엔진 측면에서는 런타임과 GC (가비지 컬렉션)의 존재로 인하여 C++이 더 적합한 선택지라 말할 수 있다. 해당 영역에서는 일시적인 프리징이나 최적화의 문제가 치명적인 결과로 도래할 수 있기 때문이다. 이는 다르게 말하자면, 상대적으로 해당 문제들의 영향이 덜한 상위 차원 로직에서는 LINQ, 패턴 매칭 등의 개발 편의 문법들의 중요도가 높아진다는 뜻이다.

두 번째 이유는 C++과의 상호 운용성이다. 앞서 언급하였듯이 Minecraft: ONE의 심장부는 C++로 작성된다. C#은 역사적으로 초기부터 C++과의 상호 운용을 고려하고 개발되었기에, 상위 차원 로직의 개발에서 요구하는 고수준 언어 중 C++과의 연동성이 가장 부각되는 언어라 말할 수 있다. 이러한 장점은 .NET의 최신 버전으로 향할 수록 더더욱 부각되며, .NET 10 기준 `[LibraryImport]`와 함수 포인터를 통해 오버헤드 및 레이턴시를 최소화하여 개발할 수 있다. `[LibraryImport]`와 함수 포인터는 Minecraft: ONE의 개발 시 적극적으로 활용한다.

세번째 이유는 과거를 상회하는 C#의 완성도이다. 2011년 Bedrock Edition의 전신인 Pocket Edition의 개발 당시의 C#은 .NET Framework라는 Windows에 종속된 전용 런타임에서만 구동되었으며, 실행 속도마저 현재에 비해 현저히 느린 언어였다. 이러한 점으로 인하여 크로스 플랫폼이 필수적이고 PC에 비해 사양이 낮은 모바일 기기 구동을 지원해야 하는 Pocket Edition에는 적합하지 않았고, 결국 Bedrock Edition으로 이어지는 현재까지 C++이라는 양날의 검을 사용하게 되었다.
그러나 10년이 넘는 세월이 흐른 현재, .NET Framework는 크로스 플랫폼을 지원하는 .NET으로 발전되었다. C# 또한 JIT 컴파일러의 발전과 Native AOT의 지원, 저수준 메모리 제어 기능 등 수많은 개선을 통하여 Unity의 공식 언어가 될만큼 성숙한 언어 중 하나로 분류된다. 이 시점에서 Minecraft라는 대규모 게임의 상위 차원 로직을 C++이라는 상대적인 저수준 언어로 개발할 경우, 최적화 측면에서는 부분적으로 유리할 수 있으나 긴 개발 시간과 불필요한 비용의 상승을 감수해야 한다.

Bedrock Edition은 플랫폼에 따라 그래픽 라이브러리를 서로 다른 것을 사용하였으나, 이는 최적화 측면에서는 유리하나, 코드 베이스를 전부 다른 것을 사용해야 하기에 마찬가지로 긴 개발 시간과 불필요한 비용의 상승으로 이어진다. Minecraft: ONE은 해당 문제를 해결하기 위해 오픈 소스 라이브러리 BGFX를 기반으로 자체적으로 개조한 추상화 레이어를 사용하며, DirectX (Windows, Xbox), Vulkan (Linux, Android), Metal (macOS, iOS / iPadOS), AGC (Play Station), NVN (Nintendo Switch) 환경을 하나로 통합된 코드 베이스로 개발한다. 이러한 추상화 레이어를 사용할 시 코드 베이스의 유지보수 측면에서 유리하며, 각 플랫폼의 그래픽 API와 셰이더 언어의 차이를 극복할 방법을 제공하기에 플레이 경험의 일관성에서도 장점이 더해진다.

### 배포

---

Minecraft: ONE의 내부 아키텍처는 배포 단계에서부터 실행 파일과 추가적인 모딩 레이어를 철저히 분리하도록 설계되었다. 게임 실행 파일이 위치한 본체는 .NET의 최신 기능 Native AOT를 통하여 기계어로 미리 컴파일된 상태로 배포한다. 이는 실행 성능과 메모리 효율성, 그리고 역컴파일 방지라는 보안을 확보한다. Native AOT는 단일 배포 파일을 통한 플랫폼 대응이 불가능하기에 각 플랫폼 별로 배포 파일을 빌드한다.
반면 모딩 레이어는 모딩 파일의 동적 로드 확장성이 요구되기에, 실시간으로 중간 언어로 변환 후 컴파일하는 전통적인 JIT 방식을 사용한다. 소스 코드를 난독화하지 않음으로써 모딩 생태계의 활성화를 유도하며, Native AOT의 자체적인 환경에 더해 `rd.xml`을 제공하지 않음으로써 안정성의 하락과 예기치 못한 크래시의 주범이 되는 리플렉션 의존 코드가 동작하지 못하도록 한다.

Native AOT와 JIT의 공존은 임베디드 런타임 기법을 통해 가능케 한다. Native AOT 내부에서 `nethost.dll`을 사용하여 Native AOT 위에서 별도의 JIT 런타임을 구동하며, 게임 실행 시 모드 폴더를 스캔하고 `host.fxr` 라이브러리를 통해 JIT 런타임을 초기화하여 모드들을 로드한다. 이는 Unity가 C++ 엔진 위에서 Mono/IL2CPP를 구동하는 방식과 유사하나, .NET 표준을 따른다는 차별점이 존재한다. 이 두 개의 서로 다른 실행 환경 사이의 데이터 교환 시에는 `Shared Memory`, 그리고 `Direct Pointers` 구조를 사용하여 Zero-copy의 장점인 오버헤드 및 레이턴시의 최소화를 확보한다.

배포 파일의 물리적인 크기를 줄이고 모바일 및 콘솔 환경에서의 로딩 속도를 개선하기 위하여 Native AOT 배포 시 사용하지 않는 코드를 네이티브 바이너리에서 제거하는 트리밍 기술을 적용한다. 트리밍의 부작용인 리플렉션의 오인식 제거는, Native AOT 내부에서 타입 리플렉션 대신 소스 생성기를 적극적으로 사용하여 해결한다.

역컴파일과 리플렉션은 Java Edition 모딩 생태계의 핵심 기술이며, 이를 제거할 경우 기존 모더들에게 큰 제약이 되어 생태계 구축이 어려워질 수 있다는 점을 인지하고 있다. 때문에 Minecraft: ONE은 역컴파일과 리플렉션의 배제를 상쇄할 공식 SDK과 API, 모드 로더, 소스 생성기를 지원하며, 이는 아래의 유저 모딩 부문에 자세히 서술되어 있다.
